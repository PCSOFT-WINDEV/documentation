
## AJAX: Direct procedure calls
			

<a name="NOTE1"></a>
<a name="NOTE1_1"></a>


## Overview
<a name="overview_ELTTEXTE000236"></a>
Starting with version 2024, it is no longer necessary to use [AJAXExecute](../WDLang2/3055114.md) and [AJAXExecuteAsynchronous](../WDLang2/3055115.md) to make AJAX calls. Simply call the server procedures directly from the Browser code. 

<a name="NOTE2"></a>
<a name="NOTE2_1"></a>


## Types of Server procedures
<a name="types_server_procedures_ELTTEXTE000260"></a>
Server procedures can be "automatic", "accessible" or "inaccessible". This is indicated in the procedure header.  

By default, new server procedures are set to "automatic" mode. 
<br>![](https://doc.pcsoft.fr/en-US/images/image.awp?langid=3&name=Ajax_procedures%20-%20HC%20N%B0002.gif)


Automatic mode detects if there are any calls to the server procedure written in Browser code. This includes any use of the [AJAXExecute](../WDLang2/3055114.md) function or any direct calls. The number of detected calls appears in the procedure header. 

Two other modes can be enabled via the context menu of the procedure header:<br>![](https://doc.pcsoft.fr/en-US/images/image.awp?langid=3&name=Ajax_procedures%20-%20HC%20N%B0003.gif)


- "Always accessible from Browser code" (accessible). 

- "Never accessible from Browser code" (inaccessible). 




You can force accessible mode to handle cases where calls are not automatically detected. This happens when procedures are located in external components and calls are made from the project. 

You can also force inaccessible mode. In this case, the procedure can never be called from a Browser code. 

**Note**: Procedures accessible from Browser code can be executed with malicious intent. "Inaccessible" mode provides additional security compared to automatic mode. "Automatic" mode makes the procedure inaccessible from a browser only if it has never been called from Browser code.

## AJAX procedure calls
<a name="ajax_procedure_calls_ELTTEXTE000284"></a>
"Accessible" procedures (or procedures in "Automatic" mode) can be called from Browser code. Several call syntaxes are available:

- [synchronous syntax](#NOTE3_2). 

- [asynchronous syntax](#NOTE3_3). 

- [&lt;asynchronous&gt; attribute](#NOTE3_4). 

- [automated procedure](#NOTE3_5)



<a name="NOTE3_2"></a>


### Synchronous syntax
<a name="synchronous_syntax_ELTPARAGRAPHE000071"></a>

A server procedure called from Browser code automatically triggers an AJAX request. 

This is a synchronous call, i.e., no other process is run until the result of the server procedure is received. 

Note: In previous versions, this behavior was achieved by calling AJAXExecute and using different constants. 

**Example**: 

- VerifyCaptcha() server procedure: 
	VerifyCaptcha local procedure (server)

	```wl
	PROCEDURE VerifyCaptcha()
	
	RETURN CPTCH_Form.Verify(EDT_Verification)
	```


- On the browser side, the click code of the BTN_Create_Account button calls the browser procedure: 
	Click on BTN_Create_Account (browser)

	```wl
	IF NOT VerifyCaptcha() THEN
		Error("Invalid captcha")
		SetFocusAndReturnToUserInput(EDT_Verification)
	END
	```


- Equivalent call in previous versions: 
	Click on BTN_Create_Account (browser)

	```wl
	IF NOT AJAXExecute(ajaxUpdateControl + ajaxPostValueOfControls + ajaxStructuredTypes + ...
			ajaxSynchronizeServerVariables, VerifyCaptcha) THEN
		Error("Invalid captcha")
		SetFocusAndReturnToUserInput(EDT_Verification)
		// Old function: ReturnToCapture(EDT_Verification)
	END
	```




<a name="NOTE3_3"></a>


### Asynchronous syntax
<a name="asynchronous_syntax_ELTPARAGRAPHE000100"></a>

To make an asynchronous call to a server procedure in Browser code, you need to use the AFTER .. DO statement. 

Example: Whenever modifying EDT_PostalCode (browser)

```wl
sResult is string

AFTER sResult = GetCityPostalCode() DO
	LIST_City_PostalCode.DeleteAll()
	LIST_City_PostalCode.Add(sResult)
END
```
The code between the DO and END keywords will be executed asynchronously after the "GetCityPostalCode" server procedure has been executed. The user will not be blocked while the server procedure is executed. 

Note: Equivalent call in previous versions: 
Whenever modifying EDT_PostalCode (browser)

```wl
IF AJAXAsynchronousCallPending(ID) THEN
	AJAXCancelAsynchronousCall(ID)
END

ID = AJAXExecuteAsynchronous(ajaxUpdateControls + ajaxPostValueOfControls + ajaxStructuredTypes + ...
		ajaxSynchronizeServerVariables, GetCityPostalCode, showResults) THEN

	INTERNAL PROCEDURE showResults(sResult string)
		LIST_City_PostalCode.DeleteAll()
		LIST_City_PostalCode.Add(sResult)
	END
```

<a name="NOTE3_4"></a>


### &lt;asynchronous&gt; attribute
<a name="attribute_ELTPARAGRAPHE000122"></a>

With asynchronous syntax, the calls to the server procedure are not executed simultaneously. Calls are executed in succession. 

Thus, if the procedure is called 5 times, the 5th call will be launched only when the first 4 have been completed. 

To execute multiple calls simultaneously, simply use the **&lt;asynchronous&gt;** attribute in the declaration of the procedure. In this mode:

- the procedure is executed in a secure thread on the server. The main thread is therefore not blocked. 

- it is not possible to access the controls in the page. In this mode, the procedure generally receives the contents of the controls as parameters and returns the values to be displayed. 




Example: GetCityPostalCode local procedure (server)

```wl
PROCEDURE GetCityPostalCode(sPostalCode) <asynchronous>

arrResults is array of strings
QRY_POSTALCODES.ParamPostalCode = SPostalCode
HExecuteQuery(QRY_POSTALCODES)
FOR EACH QRY_POSTALCODES
	ArrayAdd(arrResults, QRY_POSTALCODES.PostalCode + " " + QRY_POSTALCODES.CITY)
END
RETURN arrResults
```
As execution is asynchronous, the last call sent to the server is not always the one that ends last. It may be necessary to ensure that the code between DO and END is only triggered when the result of the last server call is received. To do so, use the **&lt;last call&gt;** attribute in the procedure declaration. 

Example: 

- Server WLanguage procedure: 
	AsynchronousProcedure_ReturnLastCall (server)

	```wl
	PROCEDURE AsynchronousProcedure_ReturnLastCall(Param) <asynchronous, last call>
	ThreadPause(1s)
	Trace('AsynchronousProcedure_ReturnLastCall([%Param%])')
	RETURN "ReturnLastCall=[%Param%]"
	```


- Procedure call: 
	Procedure call (browser)

	```wl
	INTERNAL PROCEDURE CallProcedure() <delay=10cs>
		AFTER r = AsynchronousProcedure_ReturnLastCall(1) DO
			EDT_Trace += [CR] + 'After AsynchronousProcedure_ReturnLastCall(1) => [%r%]'
			EDT_Trace += [CR] + TraceGet()
		END
	END
	```

### Automated procedure
<a name="automated_procedure_ELTPARAGRAPHE000161"></a>

Automated procedures can be used to define whether a server procedure is synchronous or asynchronous. 

To define automated procedures:

1. Open the code of the procedure.

2. Open the automated procedure description window:

	- Click ![](https://doc.pcsoft.fr/en-US/images/image.awp?langid=3&name=Proc_auto_WB%20-%20HC%20N%B0001.gif) in the procedure header.

	- Select "Configure the automated processes of the procedure" in the context menu of the procedure ("Project explorer" pane).

	- Select "Properties" in the context menu of the procedure in the "Code" pane.




3. In the window that appears: <br>![](https://doc.pcsoft.fr/en-US/images/image.awp?langid=3&name=Proc_auto_WB%20-%20HC%20N%B0002.gif)


	- Select "Asynchronous execution". 

- Check "In case of concurrent calls, return only the last call" (if necessary). This option is equivalent to the "**&lt;last call&gt;**" attribute. 
			

4. Confirm. An icon appears next to the procedure name to indicate that an automation has been applied. <br>![](https://doc.pcsoft.fr/en-US/images/image.awp?langid=3&name=Proc_auto_WB%20-%20HC%20N%B0003.gif)
