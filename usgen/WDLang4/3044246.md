


## Implement journaled replication: Modify database schema
			



<a name="NOTE1"></a>
<a name="NOTE1_1"></a>


## Overview
<a name="overview_ELTTEXTE000187"></a>
Log-based replication can be implemented in the data model editor:

- directly when creating a table, or. The table creation wizard asks if log replication is to be managed for this table.

- on an existing table (whether or not the application has been released).




<a name="NOTE2"></a>
<a name="NOTE2_1"></a>


## Managing log-based replication for a table
<a name="managing_logbased_replication_for_table_ELTTEXTE000211"></a>
To implement log replication on a table:

1. Open your database schema in the table model editor.

2. For all replicated tables, check the "Log-based replication (for compatibility with the earlier versions)" option ("Miscellaneous" tab in the table description). If your tables do not comply with the conditions for using replication (see next paragraph), various messages are displayed.
	**Caution**: when setting up journaled replication, logging is automatically set up.. Logging is a simple way of keeping track of all operations carried out on tables so that they can be transferred to the various databases. For more details on logs, see [The log process](../WDLang4/3044184.md).

3. Generate your database schema.

## Consequences of implementing log-based replication
<a name="consequences_implementing_logbased_replication_ELTTEXTE000235"></a>


### Required or recommended conditions
<a name="required_recommended_conditions_ELTPARAGRAPHE000041"></a>

When implementing log-based replication on a table, WINDEV and WEBDEV:

- **Use an 8-byte automation identifier in log file replication**: 
	To simplify log-based replication, we recommend that you use an automatic identifier in your tables. This automatic identifier is entirely managed by WINDEV and WEBDEV. To avoid the duplicate errors during the replication, ranges of identifier numbers are allocated to each site involved in the replication. 
	The use of an automatic identifier is highly recommended but not mandatory. Indeed, you always have the ability to manage a custom identifier containing, for instance, an automatic identifier and the initials of the site or person creating the record.

- **Implement the log process for the selected table**: 
	Logging is a simple way of keeping track of all operations carried out on tables so that they can be transferred to the various databases. The "Log of write operations + history of accesses" log process is automatically implemented when "Log-based replication" is checked.

### Directory for creating the files required by the log-based replication
<a name="directory_for_creating_the_files_required_the_logbased_replication_ELTPARAGRAPHE000057"></a>

Log-based replication is closely linked to the log process. The log process is automatically enabled when log-based replication is implemented in an application.

For all the tables used (tables, log files or replication files), the paths of the corresponding physical files can be defined in the data model editor or programmatically.

## Generating the database schema
<a name="generating_the_database_schema_ELTTEXTE000265"></a>
To take into account the implementation of log-based replication in the database schema, **you must generate the database schema.**

If the application already handles tables, this database schema generation triggers an automatic modification of the tables in order to: 

- take log-based replication into account,

- take the log process into account (if necessary)

- implement the automatic identifiers.




This modification of the tables will also have to be performed when installing the application (if the application was already deployed).

**Attention**: If logs already exist, they are automatically purged during the automatic modification. Before starting the automatic modification, the existing logs can be saved by WDLog.
