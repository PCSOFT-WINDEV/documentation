


## GDS : Politique de réintégration
			



<a name="NOTE1"></a>
<a name="NOTE1_1"></a>


## Présentation
<a name="presentation_ELTTEXTE000210"></a>
Le GDS offre la possibilité de définir une politique de réintégration. Cette politique de réintégration sera appliquée lors de : 

- [la réintégration d'un élément dans la base de source du GDS](../Editeurs/2038007.md). 

- [l'historisation locale d'un élément](../Editeurs/2510003.md). 
	




Il suffit de définir les critères à remplir pour qu'un élément du projet puisse être réintégré dans la base de sources du GDS. Parmi les critères possibles :

- Pas d'erreur de compilation,

- Lancement au moins d'un test de l'élément, etc.




Ces règles peuvent être obligatoires ou non. En cas de non respect, le développeur peut être tenu de fournir une explication.

<a name="NOTE2"></a>
<a name="NOTE2_1"></a>


## Comment le faire ?
<a name="comment_faire_ELTTEXTE000243"></a>


### Définir une politique de réintégration
<a name="definir_une_politique_reintegration_ELTPARAGRAPHE000036"></a>Pour définir une politique de réintégration : 

1. Sous le volet "GDS", dans le groupe "Base GDS", déroulez "Gérer" et sélectionnez "Politique de réintégration".<br>![](https://doc.pcsoft.fr/fr-FR/images/image.awp?langid=5&name=GDS_Politique.gif)


2. Sélectionnez les règles à respecter par les éléments réintégrés. Ces règles sont regroupées par thème sur plusieurs onglets : "Général", "Tests automatiques", "Métrique de code" et "Plan d'action". 

3. Indiquez les options générales de la politique de réintégration (ces options sont affichées quel que soit l'onglet sélectionné) :  

	- Toujours ignorer les règles sur le projet (wdp) : Permet de ne pas prendre en compte les règles lors de la manipulation du fichier du projet (fichier wdp).

	- Possibilité d'ignorer les règles.

	- Saisie obligatoire d'un commentaire en cas de règle non respectée.




4. Validez. La politique de réintégration est automatiquement prise en compte pour le projet en cours.




**Remarque** : Il est également possible de définir la politique de réintégration depuis l'administrateur du GDS (option "Politique de réintégration" du menu contextuel d'un projet).
<a name="NOTE2_2"></a>


### Fonctionnement de la politique de réintégration
<a name="fonctionnement_politique_reintegration_ELTPARAGRAPHE000069"></a>Si l'élément réintégré ne respecte pas la politique de réintégration définie pour le projet : 

- en cas d'obligation de saisie d'un commentaire, un toast est affiché. <br>![](https://doc.pcsoft.fr/fr-FR/images/image.awp?langid=5&name=GDS_NonRespect.gif)


- en cas de non respect d'une des autres règles, la fenêtre suivante apparaît : <br>![](https://doc.pcsoft.fr/fr-FR/images/image.awp?langid=5&name=GDS_Politique%20-%20HC%20N%B0003.gif)
Cette fenêtre présente les différentes règles non respectées. 




Si l'utilisateur a la possibilité d'ignorer les règles, il peut cocher l'option "Réintégrer quand même".

Si un commentaire explicatif doit être saisi pour ignorer les règles, le bouton de validation de cette fenêtre sera dégrisé uniquement lorsque le commentaire sera saisi dans la zone correspondante.

Le bouton "Editer la politique..." permet d'éditer et de modifier si nécessaire les règles de la politique de réintégration.
<a name="NOTE2_3"></a>


### Stockage et manipulations de la politique de réintégration
<a name="stockage_manipulations_politique_reintegration_ELTPARAGRAPHE000096"></a>La politique de réintégration est stockée dans un fichier "PolitiqueDeReintegration.gds" à la racine du répertoire du projet. Ce fichier est présent dans le GDS comme tous les fichiers du projet. Ce fichier est partageable entre plusieurs projets.

Il est possible d'attribuer des droits spécifiques au fichier correspondant à la politique de réintégration (par exemple pour que seul le chef de projet puisse modifier ce fichier).

Si le fichier "PolitiqueDeReintegration.gds" est présent dans le répertoire parent, tous les nouveaux projets créés utiliseront cette politique de réintégration.

**Astuce** : Dans le cas d'une branche, il est possible de définir une politique de réintégration plus restrictive.

## Les différentes règles en détail
<a name="les_differentes_regles_detail_ELTTEXTE000279"></a>


### Onglet "Général"
<a name="onglet_general_ELTPARAGRAPHE000111"></a>Les différentes règles de réintégration proposées par l'onglet "Général" sont les suivantes :

- Aucune erreur de compilation : Pour être réintégré, l'élément ne doit comporter aucune erreur de compilation.

- Aucun warning de compilation : Pour être réintégré, l'élément ne doit comporter aucun warning de compilation.

- Aucune information de compilation : Pour être réintégré, l'élément ne doit comporter aucune information de compilation.

- Aucune erreur de norme de programmation : Pour être réintégré, l'élément ne doit comporter aucune erreur de norme de programmation. Cette norme de programmation est définie dans l'onglet "Compilation" de la fenêtre de description du projet. Pour plus de détails, consultez [Description du projet : Onglet Compilation](../Editeurs/9500218.md). 

- L'élément réintégré doit être associé à une tâche ou un incident : Cette option permet de lier l'élément réintégré à une tâche ou un incident présent dans le Centre de Gestion de Projets. 

- Un commentaire doit être saisi lors de la réintégration.

- Le projet doit avoir été testé (GO) au moins une fois après une modification : Permet d'obliger le développeur à tester sa modification. 

- Toujours ignorer les règles sur le projet (wdp) : Permet de ne pas prendre en compte les règles lors de la manipulation du fichier du projet (fichier wdp).

	- Ces règles peuvent être ignorées : Permet à l'utilisateur d'ignorer les règles de réintégration (par exemple dans certains cas spécifiques). Dans ce cas, l'option "Un commentaire doit être saisi pour ignorer les règles" permet de rendre obligatoire la saisie d'un commentaire en cas de règle non respectée.






<a name="NOTE3_2"></a>


### Onglet "Tests automatiques"
<a name="onglet_tests_automatiques_ELTPARAGRAPHE000136"></a>Les différentes règles de réintégration proposées par l'onglet "Tests automatiques" sont les suivantes :

- Chaque élément doit avoir au moins 1 test automatique. 
	Attention : si cette règle est sélectionnée, elle s'applique à tous les éléments, même au fichier projet (".WDP"), qui contient notamment le code d'initialisation du projet.

- Aucun test automatique en erreur.



<a name="NOTE3_3"></a>


### Onglet "Métrique de code"
<a name="onglet_metrique_code_ELTPARAGRAPHE000148"></a>L'onglet "Métrique de code" permet de saisir le taux de pourcentage de commentaires de code minimal à respecter.
<a name="NOTE4_3"></a>


### Onglet "Plan d'action"
<a name="onglet_plan_action_ELTPARAGRAPHE000155"></a>L'onglet "Plan d'action" permet de définir le plan d'action à exécuter lors de la réintégration du projet. Si un plan d'action doit être exécuté, il est nécessaire d'indiquer : 

- le coordinateur de la fabrique logicielle utilisée, 

- le port du coordinateur, 

- l'utilisateur et le mot de passe associé. 


Le plan peut être choisi parmi les plans existants sur le coordinateur.
